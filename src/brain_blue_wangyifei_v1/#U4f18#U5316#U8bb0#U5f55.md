## 2026-07-31：修正 1 号机器人角色配置

状态：已修改

### 哪里错了

`manifest.yaml` 中 v3 角色设计明确写明 1 号机器人是 `goal_keeper`，但 `config/config.yaml` 中实际运行配置为：

```yaml
player_id: 1
player_role: "defender"
```

这会导致 1 号机器人以后卫身份启动，而不是守门员。

### 为什么错

行为树根据黑板中的 `player_role` 选择分支：

```xml
<SubTree ID="StrikerPlay" _while="player_role == 'striker'" />
<SubTree ID="GoalKeeperPlay" _while="player_role == 'goal_keeper'" />
<SubTree ID="DefenderPlay" _while="player_role == 'defender'" />
```

因此 `player_id: 1` 配成 `defender` 后，1 号不会走守门员逻辑，也不会承担 v3 设计中的门球执行职责。

### 比赛后果

- 1 号不守门，后防结构从开局就是错的。
- 己方门球时，v3 逻辑要求 `goal_keeper` 执行，配置错误会导致门球执行权异常。
- 队内通信会把 1 号广播成 `defender`，其他机器人也会按错误角色协作。
- 后卫和守门员站位目标不同，可能造成门前空位和失球。

### 怎么改

已将 `config/config.yaml` 修改为：

```yaml
player_id: 1
player_role: "goal_keeper"
```

### 如何测试

1. 启动 1 号机器人，确认日志中角色为 `goal_keeper`。
2. 普通 `PLAY` 状态下，确认 1 号进入 `GoalKeeperPlay`，不是 `DefenderPlay`。
3. 模拟己方 `GOAL_KICK`，确认 1 号 `freekick_i_am_taker=true`，其他机器人为 false。
4. 检查队内通信包，确认 1 号广播角色为 `goal_keeper`。

## 2026-07-31：优化倒地起身恢复状态机

状态：已修改

### 哪里错了

`src/brain_tree.cpp` 中 `CheckAndStandUp::tick()` 原来只在行为树节点被 tick 到时尝试一次 `standUp()`，并且用 `currentRobotModeIndex == 1/10/8/20` 这种底层模式号硬判断恢复过程。`src/brain.cpp` 的 `Brain::tick()` 没有在最开头短路恢复状态，所以倒地、正在起身时仍可能继续走 `handleCooperation()`、行为树和 `pubKickMsg()`。

### 为什么错

倒地恢复是全局安全状态，不应该藏在行为树中间。只要行为树还继续执行，后面的 chase、kick、assist、定位球执行权、视觉踢球退出逻辑都有机会覆盖恢复动作。底层模式号也不能当作唯一状态机依据，因为通信延迟或模式号变化会让重试和成功判断失效。

### 比赛后果

- 倒地机器人仍可能发速度或踢球指令，起身动作被 chase/kick 打断。
- 倒地前锋仍可能广播自己可抢球、可领导，队友看到通信后让位，导致无人真正控球。
- 定位球期间倒地机器人可能仍被认为是执行者，造成执行权混乱甚至违规。
- 反复倒地或起身失败时没有清晰冷却和重试边界，容易在底层恢复模块和上层行为树之间互相打架。

### 怎么改

1. 在 `Brain::tick()` 最开头调用 `handleRecovery()`，只要恢复状态机处于 `FALLING/FALLEN_WAIT/GETTING_UP/VERIFYING/FAILED_COOLDOWN` 或底层状态仍是 `IS_FALLING/HAS_FALLEN/IS_GETTING_UP`，立即停速、退出视觉踢球、清空抢球和定位球执行权，然后 `return`，不进入行为树。
2. 在 `BrainData` 新增恢复 FSM 字段：`recoveryFsmState`、状态进入时间、上次起身时间、验证时间、冷却时间、重试计数和是否已请求起身。
3. 新状态机为：`IDLE -> FALLING -> FALLEN_WAIT -> GETTING_UP -> VERIFYING -> IDLE`，失败后进入 `FAILED_COOLDOWN` 再回到 `FALLEN_WAIT`。
4. `standUp()` 不再只发一次：倒地稳定 500ms 后发起身；如果 4000ms 后仍是 `HAS_FALLEN` 且恢复可用，则重试；最多 3 次；超过后进入 3000ms 冷却。
5. 起身成功以 `recoveryState == IS_READY` 为主，并排除仍处于起身模式的 `currentRobotModeIndex == 10`；成功后再验证 500ms，避免刚抖到 ready 就恢复比赛行为。
6. 队内 UDP 线程继续运行，但恢复期间广播语义改为“在线但不可用”：`isAlive=false`、`isLead=false`、`isInVisualKick=false`、`ballDetected=false`、`ballLocationKnown=false`、`cost=1e6`。
7. 修复 `recoveryStateCallback()` 的 RawBytes 解析：检查包长度和状态枚举范围，避免 `memcpy()` 按错误长度覆盖栈内存或状态数组越界。

### 如何测试

1. 发布 `IS_FALLING -> HAS_FALLEN`，确认日志进入 `FALLING/FALLEN_WAIT`，机器人每帧发零速度，不再 tick 行为树，不再发布踢球。
2. `HAS_FALLEN` 保持超过 500ms 且 `isRecoveryAvailable=true`，确认只发一次 `standUp()`，状态进入 `GETTING_UP`。
3. 让底层保持 `IS_GETTING_UP` 超过 4000ms，确认不会重复发 `standUp()`；只有状态回到 `HAS_FALLEN` 且超时才重试。
4. 连续失败 3 次，确认进入 `FAILED_COOLDOWN`，3 秒内不继续刷起身指令。
5. 发布 `IS_READY` 且 `currentRobotModeIndex != 10`，确认进入 `VERIFYING`，稳定 500ms 后回到 `IDLE`，下一帧才恢复行为树。
6. 恢复期间抓 UDP 包，确认仍有广播，但 `isAlive=false`、`isLead=false`、`cost=1e6`，其他队友不会把倒地机器人当抢球者。
7. 发布长度小于 `RobotRecoveryStateData` 或状态值大于 3 的 RawBytes，确认只记录错误日志，不崩溃、不写入非法状态。

## 2026-07-31：修复运行时角色与 lead 判断不同步

状态：已修改

### 哪里错了

`src/brain.cpp` 的 `Brain::handleCooperation()` 里原来只用：

```cpp
string selfRole = config->get_player_role();
```

这个值来自配置文件，是初始角色。可是比赛中代码会通过黑板动态修改 `player_role`，行为树实际也是按黑板里的 `player_role` 选择 `StrikerPlay`、`GoalKeeperPlay`、`DefenderPlay`。

旧代码在 v3 lead 限制里仍然用初始角色判断：

```cpp
if (selfRole == "defender" || selfRole == "goal_keeper") {
    wantLead = false;
}
```

这会导致运行时角色和抢球资格不同步。

### 为什么错

角色有两个来源：

- `config->get_player_role()`：配置里的初始角色，只适合用于 INITIAL/READY 时恢复默认阵型。
- `tree->getEntry<string>("player_role")`：当前运行角色，行为树真正按它分支。

旧逻辑把两者混用。结果是行为树认为机器人已经切成某个角色，但 lead 判断还按配置角色处理。

### 比赛后果

- 初始守门员动态切成 striker 后，行为树进 `StrikerPlay`，但 lead 判断仍按 `goal_keeper` 禁止抢球，导致该抢的不抢。
- 初始前锋动态切成 `goal_keeper` 或 `defender` 后，lead 判断仍可能按 striker 身份保留抢球权，UDP 可能广播错误的 `isLead=true`。
- 角色切换后旧 `decision='chase'/'kick'` 可能残留一帧，造成切角色后继续执行旧动作。

### 怎么改

在 `handleCooperation()` 中拆分初始角色和当前角色：

```cpp
const string initialRole = config->get_player_role();
string currentRole = tree->getEntry<string>("player_role");
```

新增本地 `setRuntimeRole(role, reason)`，本函数内所有运行时角色切换都通过它：

```cpp
setRuntimeRole("striker", "field_not_full");
setRuntimeRole("goal_keeper", "teammate_goalie_switch_cmd");
setRuntimeRole(initialRole, "ready_full_team_restore");
```

`setRuntimeRole()` 会同步更新 `currentRole`，并清空旧行为：

```cpp
player_role = role;
decision = "";
assist_kick = false;
assist_chase = false;
go_manual = false;
```

lead 资格判断改为使用当前运行角色：

```cpp
if (currentRole == "defender" || currentRole == "goal_keeper") {
    wantLead = false;
}
```

INITIAL/READY 满员恢复默认阵型仍使用 `initialRole`。

### 如何测试

1. 初始 `player_role=goal_keeper`，运行时切成 `striker`，确认日志中 `currentRole=striker`，且 lead 判断不再按 `goal_keeper` 禁止抢球。
2. 初始 `player_role=striker`，运行时切成 `goal_keeper`，确认 `currentRole=goal_keeper` 后 `wantLead=false`，UDP 不再广播错误 lead。
3. 触发 `gc_game_state=INITIAL`，确认 `player_role` 恢复配置角色，`decision` 被清空。
4. 触发 READY 满员恢复，确认 `player_role` 恢复配置角色，且没有残留 `chase/kick/assist_chase/assist_kick/go_manual`。
5. 检查日志 `initialRole/currentRole/wantLead/stableLead`，确认角色切换当帧 lead 判断使用的是当前角色。

## 2026-07-31：限制守门员普通比赛中过远 chase

状态：已修改

### 哪里错了

`src/brain_tree.cpp` 的 `GoalieDecide::tick()` 在普通比赛分支中，原逻辑只按球的场上 X 坐标和 `chase_threshold` 判断：

```cpp
if (ball.posToField.x > 0 - retreat_hysteresis) {
    decision = "retreat";
} else if (ballRange > chase_threshold) {
    decision = "chase";
} else if (angleIsGood) {
    decision = "kick";
} else {
    decision = "adjust";
}
```

这会导致只要球还在己方半场，且距离守门员超过阈值，守门员就可能主动 chase。代码没有限制守门员的最大出击深度，也没有区分“普通己方半场球”和“真正威胁球门的禁区球”。

### 为什么错

守门员的首要职责是守门线和封堵射门角度，不是参与普通抢球。只要球没有进入本方门区/禁区危险走廊，守门员离开球门的收益很低，风险极高。原逻辑会把守门员从门前拉出去，尤其在球位于己方半场但离球门仍较远时，守门员会做出类似前场球员的 chase 行为。

### 比赛后果

- 守门员离门过远，门前直接空掉。
- 对手斜传、远射或二点球时，我方没有最后一道防线。
- 守门员和后卫、前锋重复抢同一个己方半场球，防守阵型被破坏。
- 一旦守门员 chase 失败或被绕过，失球概率明显升高。

### 怎么改

已修改 `GoalieDecide::tick()` 的普通比赛分支：

1. 保留我方 `GOAL_KICK` 的守门员发球逻辑不变。
2. 普通比赛时新增本方球门坐标、本方门区前沿、本方禁区前沿判断。
3. 只有球进入本方门区附近或本方禁区走廊时，才认为 `ballThreatensGoal=true`。
4. 如果球不威胁球门，守门员直接 `retreat`，回到封堵位。
5. 如果守门员已经超过本方禁区前沿 0.5m，且球不在 0.9m 脚边清球范围内，也强制 `retreat`。
6. 只有满足危险球条件且没有出击过深时，才允许继续 `chase/kick/adjust`。

核心伪代码：

```cpp
selfGoalX = -fieldLength / 2
ownGoalAreaFrontX = selfGoalX + goalAreaLength
ownPenaltyFrontX = selfGoalX + penaltyAreaLength

ballInGoalMouth =
    ball.x <= ownGoalAreaFrontX + 0.50 &&
    abs(ball.y) <= goalAreaWidth / 2 + 0.50

ballInPenaltyCorridor =
    ball.x <= ownPenaltyFrontX + 0.35 &&
    abs(ball.y) <= penaltyAreaWidth / 2 + 0.40

ballThreatensGoal = ballInGoalMouth || ballInPenaltyCorridor
goalieTooFarOut = robot.x > ownPenaltyFrontX + 0.50

if (!ballThreatensGoal)
    decision = "retreat"
else if (goalieTooFarOut && ballRange > 0.90)
    decision = "retreat"
else if (ballRange > chaseThreshold)
    decision = "chase"
else if (angleIsGood)
    decision = "kick"
else
    decision = "adjust"
```

### 如何测试

1. 球在中线附近或普通己方半场边路时，守门员应输出 `goalie-retreat`，不能输出 `goalie-chase`。
2. 球进入本方禁区走廊，且守门员未出击过深时，允许 `goalie-chase`。
3. 球在守门员 0.9m 脚边时，即使守门员略微出击过深，也允许 `kick/adjust` 快速清球。
4. 守门员 X 坐标超过本方禁区前沿 0.5m，且球不在脚边时，下一帧必须输出 `retreat`。
5. 我方 `GOAL_KICK` 场景不受影响，仍走原来的门球发球逻辑。

## 2026-08-04: v1 deterministic 5v5 role assignment and lead separation

Status: implemented; XML/YAML validation passed; full ROS2 build not run in this Windows shell because `colcon` and a C++ compiler are not installed in PATH.

### Scope

- Baseline copy was created from `wangyifei_v1` first.
- The working folder was initially named `wangyifei_v2` because of the original request, then renamed to `wangyifei_v1` after the correction.
- `wangyifei_v1` was used only as a read-only baseline and was not edited.

### Existing logic before this change

1. `game.player_id` and `game.player_role` came from `config/config.yaml`; `BrainTree::initEntry()` copied `player_role` to the blackboard.
2. Runtime behavior only distinguished `striker`, `goal_keeper`, and `defender` in `game.xml` and UDP communication.
3. `Brain::handleCooperation()` mixed role switching and lead election. When the team was not full, old logic could force robots into `striker`, which compressed roles by situation instead of assigning stable tactical jobs.
4. `tmMyCostRank` ranked ball-handling cost. `myStrikerIDRank` ranked old striker IDs and was reused for support/READY positioning.
5. `game.xml` routed PLAY and FREE_KICK branches by `player_role`; midfielder and secondary striker were not real runtime roles.
6. READY/SET/PLAY had kickoff handling, but ordinary kickoff did not expose a deterministic `is_kickoff_taker` separate from `is_lead`.

### Problems fixed

- No explicit runtime roles for midfielder, primary striker, and secondary striker.
- Role and lead were coupled, making stable tactical assignment and dynamic ball ownership hard to reason about.
- Missing teammates could trigger coarse role switching, while short communication gaps and long offline states were not separated.
- Recovered teammates could rejoin tactical assignment too quickly.
- Communication did not publish assigned role, current lead ID, or availability state.
- READY positioning still depended mainly on old striker rank instead of explicit tactical role.

### New architecture

The runtime role set is now:

- `goalkeeper`
- `defender`
- `midfielder`
- `primary_striker`
- `secondary_striker`

`player_role` remains the BehaviorTree dispatch key for compatibility, but it now carries the explicit runtime role. `assigned_role` is also written to the blackboard for diagnostics and future nodes.

Role assignment is deterministic and local on every robot:

- Every robot builds the same availability set from GameController penalty state, local recovery state, odom calibration, teammate UDP freshness, and teammate alive flag.
- Candidate priority lists are read from `strategy.roles.candidates.*`.
- Job preservation by available player count is: goalkeeper, primary striker, defender, midfielder, secondary striker.
- A robot can occupy only one role; once assigned to a higher-priority job it is removed from lower-priority candidate pools.

Availability states:

- `ACTIVE`: may hold a role and may compete for lead.
- `TEMPORARILY_MISSING`: short communication gap; keeps role assignment but cannot become lead.
- `UNAVAILABLE`: penalty, recovery, explicit not alive, or long communication timeout; triggers role reassignment.
- Rejoining after `UNAVAILABLE` requires `strategy.roles.rejoin_stable_msecs` before participating in role assignment again.

Lead is separate from role:

- `assignedRole` is the stable tactical job.
- `is_lead` means current ball-control responsibility.
- `current_lead_id` is deterministic and communicated.
- Goalkeeper is excluded from ordinary open-play lead election; goalkeeper still handles dangerous balls inside `GoalKeeperPlay`.
- Own ordinary kickoff uses `is_kickoff_taker` and `kickoff_taker_id` in READY/SET, then temporarily locks lead to the taker at PLAY start until ball movement or timeout releases it.

### Lead switching example

- P4 as `primary_striker` normally has the lowest role penalty and tends to keep lead.
- P5 as `secondary_striker` can become lead when its shaped cost is better by the configured margin and the candidate is stable for `lead_switch_stable_msecs`.
- P2 as `defender` can become lead only if ball handling cost overcomes the larger defender penalty, which mainly happens in the own-half/danger context.
- A recovering or temporarily missing robot cannot become lead.

SET:

- Robots stand still under existing SET tree.
- Kickoff taker identity remains stable.

PLAY start:

- If own kickoff is still active, lead is locked to `kickoff_taker_id`.
- Other robots are non-lead and stay in support behavior.

Kickoff release:

- Ball moved more than `strategy.roles.kickoff_complete_distance`, or
- kickoff elapsed more than `strategy.roles.kickoff_timeout_msecs`.
- After release, normal dynamic lead election resumes.
